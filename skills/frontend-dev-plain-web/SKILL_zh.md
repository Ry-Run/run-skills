# 前端开发（纯 CSS、HTML、JS）

## 快速上手

目标：用最小必要流程交付纯前端页面，而不是把研究、图片搜集、失败重试、实现和验证临时拼凑在一起。

## 最适合的场景

- 落地页、静态页、简单交互页。
- 明确要求优先保持纯 HTML、CSS，只有在必要时才引入 JavaScript 的任务。
- 从需求、参考图、参考站点或粗略想法直接进入代码实现。
- 完成前需要做完整浏览器验证的页面工作。

## 推荐工作流

1. 先收敛页面目标、约束和关键交互。
2. 先判断是否真的需要 JavaScript。没有明确交互、状态切换或异步行为需求时，不要加 JS。
3. 资料查证按这个顺序走：
   - `context7`：官方文档、API、标准用法。
   - `ref-skill`：GitHub 示例、issue、实战代码。
   - `grok-search`：原理解释、方案对比、最佳实践、难查的技术问题，以及所有非技术内容。若知道当前 Grok 模型，必须明确说明。
4. 如果页面需要图片，先用文字描述所需场景，再生成搜索关键词，用 `grok-search` 搜索 Unsplash、Pexels、Pixabay、Google Custom Search JSON API 等候选图片来源，再通过 `desktop-commander` 下载到本地。
5. 每张候选图片都必须先校验再使用：
   - 如果图片链接返回 `404`、`403`、超时、重定向异常或其他失败情况，就换一张图继续下载。
   - 如果下载到本地后打不开、损坏、格式异常，或浏览器里不能正常显示，也必须换图。
   - 最终 HTML 或 CSS 只能引用本地图片路径，不能把远程候选 URL 留在最终代码里。
6. 如果页面存在 Hero、展示区、主卡片等图片型区域，图片失败时不允许退化成纯色块、渐变块或 placeholder，必须继续换图直到拿到可用真图。
7. 如果环境里可用，先用 `frontend-design` 约束页面结构与视觉方向。
8. 如果环境里可用，在生成 UI 时带上 `uncodixfy`，避免落入泛化 AI 页面风格。
9. 本地实现与文件操作交给 `desktop-commander`。布局上要保证 footer 自然位于页面底部，内容少时也不会悬在中间，底下不允许留下大片空白。
10. 主流程验证优先使用 `playwright-skill`。
11. 必须进入 `chrome-devtools` 检查 console、network、布局、图片加载和 footer 位置。
12. 只有确实需要响应式适配时，再用 `adapt`。
13. 只有页面主体稳定后，再用 `polish` 做收尾。

## 图片处理循环

图片选择不是一次性动作，而是一个必须收敛到“可用本地图”的循环：

1. 先描述所需画面。
2. 生成更准确的搜索关键词。
3. 搜索候选图片。
4. 下载其中一张到本地。
5. 检查本地文件是否真实可用。
6. 任一步失败，就丢弃该候选图并换下一张。
7. 只有当页面引用的是可正常渲染的本地图时，才算完成。

## 图片优先提示词块

当页面需要强视觉图片时，可以在生成阶段附带这段精炼规则：

```text
你是一个高端、专业的前端设计师和 UI/UX 专家。

现在请优先使用纯 HTML 和 CSS 生成完整响应式网页。只有当需求明确需要交互时，才加入 JavaScript。

严格遵守以下规则：
1. 必须优先使用真实高清照片作为主要视觉元素，不要用纯色背景块、渐变色块或 placeholder 图片代替图片位置。
2. Hero 区如果需要大视觉冲击，优先使用真实大图背景，并加深色半透明 overlay 保证文字可读。
3. 卡片、展示区、内容区在需要图片时，优先使用真实图片，通过 `<img>` 或 `background-image` 呈现。
4. 如果没有现成图片，先描述画面、生成搜索关键词、搜索图片来源、下载到本地，再在最终 HTML 或 CSS 中引用本地图片路径。最终代码里不能保留临时远程图片 URL。
5. 如果某个图片链接返回 404、下载结果损坏、或者浏览器里无法显示，就必须换图继续，不能退化成纯色块或渐变块。
6. 没有明确交互需求时，不要生成任何 JavaScript。
7. 页面必须现代、美观、响应式，并具备合理的 hover 效果、平滑过渡和良好的移动端适配。
8. footer 必须自然排在页面最底部；当内容较少时，footer 也要被推到底部，下面不允许有大片空白。
```

## 验证清单

- 页面能正常加载。
- 核心交互可用。
- 要求覆盖的视口下布局正常。
- 没有明确需求时，不应引入 JavaScript，包括不必要的 `<script>`、内联事件和额外 JS 文件。
- 需要图片时，图片应为真实资源，最终由本地路径引用，不能把远程候选 URL 留在最终代码中。
- 图片必须真实可用，不能存在 `404`、`403`、broken image、文件损坏或浏览器无法解码的情况。
- 图片型区域不能被纯色块、渐变块或 placeholder 偷换。
- footer 在内容少的情况下也必须贴底，下面不能留大片空白。
- 必须通过 `chrome-devtools` 检查明显的 console、network、图片加载和布局问题。

## 约束与红线

- 默认保持轻量，不要一上来就引入任务管理、Figma、GitHub、Vercel 等无关 skill。
- 不要把 JavaScript 当默认配置；HTML、CSS 能解决就不要加 JS。
- 不要把“找到一个图片链接”当成完成，必须变成可正常显示的本地文件。
- 不要用纯色块、渐变块、假图地址或坏图文件冒充图片型设计。
- 某张图失败时，应该换图继续，而不是把页面退化成色块布局。
- `chrome-devtools` 是必经检查环节，不是可选项。
- 除非用户明确要求，否则不要把纯前端页面升级成框架项目。
- 只有在确实能提升结果时，才引入可选设计类 skill。
